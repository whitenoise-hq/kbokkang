## 1. 프로젝트 개요

### 한 줄 정의

매일 열리는 KBO 경기를 승부예측하고, 맞히면 포인트를 벌어, 그 포인트로 야구 캐릭터 카드를 뽑아 도감을 채우는 개인용 모바일 앱.

### 핵심 루프

```
경기 승부예측 → 적중 시 포인트 획득 → 포인트로 카드 뽑기 → 도감 수집 → (반복)
```

### 타깃

- KBO 팬, 특히 승부예측과 수집(가챠)에 흥미가 있는 개인 유저.
- 친구 초대/대전 없이 개인이 바로 시작 가능(초기 진입장벽 최소화).

### MVP 범위

- 포함: 회원가입/로그인, 응원팀 선택, 일일 경기 승부예측, 자동 정산, 포인트, 카드 뽑기(일반/프리미엄), 도감, 중복 카드 판매.
- 제외(향후): 카드 대전(PvP), 친구 초대, 시즌/프로모션 카드(운영 단계에서 추가), 미니홈/꾸미기.

## 2. 개발 순서 (중요)

**어드민을 먼저 개발한다.** 이유: 카드 150장 규모의 데이터 관리가 필수이고, 어드민을 만들며 데이터 스키마가 확정되어 앱 개발의 기반이 된다.

**그리고 어드민 안에서는 화면(UI)을 스키마보다 먼저 만든다.**
이유: 화면을 실제로 구현해 보면 필요한 필드·상태·목록 조건이 드러나고, 그 과정에서 스키마가 바뀐다.
스키마를 먼저 확정하면 화면 작업 중에 마이그레이션을 반복해야 하므로, **화면에서 요구가 확정된 뒤 스키마를 굳힌다.**

1. **1단계** — 모노레포 기본 구조 + 공통 상수/디자인 토큰 (`packages/shared`) ✅ 완료
2. **2단계** — **어드민 화면(UI) 구현** (`01_어드민기획서.md`)
   - 목업 데이터/로컬 상태로 화면을 먼저 완성. 이 시점에는 DB에 붙이지 않는다.
   - 동시에 카드 이미지 AI 생성 작업 병행 (`03_카드프롬프트가이드.md`)
3. **3단계** — **데이터 스키마 확정 + Supabase 세팅** (본 문서 5장)
   - 2단계에서 드러난 필드·상태·조회 조건을 반영해 확정한다.
4. **4단계** — 어드민 화면을 Supabase에 연결 (목업 → 실데이터 교체, RLS·권한 적용)
5. **5단계** — 크롤링/정산 파이프라인 (GitHub Actions) 구축 및 어드민에서 검증
6. **6단계** — 앱(Expo/RN) 개발 (`02_앱기획서.md`)

> 앱(6단계) 역시 같은 원칙을 따른다: 화면 먼저, 데이터 연결은 그 다음.

## 3. 기술 스택

| 영역           | 선택                            | 비고                                         |
| -------------- | ------------------------------- | -------------------------------------------- |
| 앱(프론트)     | Expo + React Native             | 동우 주력 스택                               |
| 어드민(프론트) | React / Next.js                 | 웹, 기능 위주 단순 UI                        |
| 백엔드         | Supabase                        | DB + Auth + Storage + (필요시)Edge Functions |
| DB             | Supabase Postgres               |                                              |
| 인증           | Supabase Auth                   | 이메일/OAuth, RLS로 유저별 데이터 격리       |
| 이미지 저장    | Supabase Storage                | 카드 이미지, S3 호환 + CDN                   |
| 크롤링/정산    | GitHub Actions (cron)           | 무료. public 레포면 완전 무료                |
| 경기 데이터    | 크롤링 (가능하면 API 우선 조사) | 결과는 전 유저 공통, 서버에서 1회만 수집     |
| 레포 구조      | 모노레포 (Turborepo + pnpm)     | 앱·어드민이 스키마/상수 공유                 |
| 앱 디자인      | 자체 토큰 (토스 스타일)         | `04_앱디자인가이드.md` 기준. 토큰은 `packages/shared/theme.ts` |
| 어드민 UI      | shadcn/ui + Tailwind            | 디자인 가이드 대상 아님. primary만 브랜드 컬러 공유 |

### 레포 구조 (모노레포)

- 레포명: **kbokkang** (GitHub kebab-case)
- npm 스코프: `@kbokkang/*`

```
kbokkang/                    (Turborepo + pnpm)
├─ apps/
│  ├─ mobile/                (Expo + React Native — 앱, @kbokkang/mobile)
│  └─ admin/                 (Next.js — 어드민, @kbokkang/admin)
├─ packages/
│  ├─ shared/                (@kbokkang/shared — Supabase 타입, 포인트 상수, 등급/카드 정의, 확률 테이블, 디자인 토큰)
│  └─ assets/                (@kbokkang/assets — 앱·어드민 공용 정적 파일. 폰트 등)
│     └─ fonts/pretendard/   (web/*.woff2 = 어드민 / native/*.otf = 앱 / LICENSE.txt)
├─ (선택) crawler/           (크롤링 스크립트. public 분리 레포로 빼면 GitHub Actions 완전 무료)
├─ docs/                     (기획서)
└─ CLAUDE.md
```

- **공통 코드는 반드시 `packages/shared`에 단일 정의.** 포인트 값·확률·등급·판매가를 앱/어드민에 중복 정의 금지(불일치 사고 방지).
- **공용 폰트/이미지 파일은 `packages/assets`에 보관.** 앱·어드민에 각각 복사해두지 않는다.
  - Pretendard는 npm 패키지(`pretendard`) 설치하지 않는다: 설치 용량 97MB이고 RN은 node_modules의 폰트를 못 쓴다. 필요한 3굵기 파일만 직접 보관(총 약 5.3MB).
  - 웹은 `.woff2`, React Native는 `.otf`/`.ttf`만 가능 → 포맷별로 `web/`, `native/` 분리.
- 크롤링은 초기엔 모노레포 내 두어도 무방(private도 무료 한도 충분). 무료 극대화하려면 public 분리 레포 검토.

### 크롤링/정산 정책

- **경기 시간대에만 30분 간격**으로 실행. 그 외 시간/경기 없는 날은 미실행.
- **실시간 정산 아님(지연 정산 허용).** 유저에겐 "집계 중" 상태로 표시.
- 적응형: 안 끝난 경기만 확인. 모든 경기 정산 완료 시 그날 작업 종료.
- 경기 결과는 모든 유저에게 동일 → 서버가 1회 수집 후 DB 저장, 앱은 읽기만. 유저 수 증가와 크롤링 비용 무관.
- GitHub Actions cron은 실행 시각이 정확하지 않을 수 있음(수 분 지연 가능) → 지연 정산이라 문제없음.

## 4. 카드 시스템 (공통 규칙)

### 4.1 등급 (5단계)

| 등급   | 코드(도감 접두어) | 색 규칙         | 레이아웃 | 반짝임 모션 |
| ------ | ----------------- | --------------- | -------- | ----------- |
| 일반   | N (Normal)        | 회색            | 박스형   | 없음        |
| 레어   | R (Rare)          | 파랑            | 박스형   | 없음        |
| 에픽   | E (Epic)          | 보라            | 박스형   | 없음        |
| 레전드 | L (Legend)        | 금              | 풀아트   | 있음        |
| 신화   | M (Mythic)        | 빨강(홀로 가미) | 풀아트   | 있음        |

- **박스형**: 캐릭터/사물이 카드 안 네모 영역에 담긴 형태(포켓몬 일반 카드 스타일).
- **풀아트**: 일러스트가 카드 전체를 채우는 형태(포켓몬 SAR 스타일).
- 반짝임 모션: 레전드/신화만. 이미지가 아니라 **앱에서 코드로** 이미지 위에 얹음.
- **등급색 실제 hex 값은 `04_앱디자인가이드.md` 1장이 단일 출처**(코드에서는 `@kbokkang/shared`의 `CARD_GRADE_META.color`). 등급색은 카드·등급 표시 전용이며 일반 UI에 남용 금지.

### 4.2 카드 종류

- **선수** (오리지널 가상 캐릭터, 특정 실존 선수 아님)
- **마스코트** (오리지널 동물 캐릭터, 특정 구단 마스코트 아님)
- **아이템** (야구 장비·응원 용품)

### 4.3 카드 이미지 원칙

- **통이미지**: 카드 1장 = 완성된 이미지 1장. 앱은 이미지 URL 하나만 호출.
- 프레임·등급 표현까지 이미지에 포함(AI 생성 시).
- **텍스트(카드 이름/등급/도감번호)는 이미지에 넣지 않음.** 앱에서 코드로 표시.
  (AI 한글 깨짐 방지 + 수정 자유 + 다국어 대응)
- IP 주의: 실존 선수·구단 로고·유니폼 디자인을 카드에 사용 금지(오리지널만).
  - 단, 응원팀 선택 화면의 구단 로고는 별도(동우 판단하에 DB에 저장해 사용 — 리스크 인지 상태).

### 4.4 도감 번호

- 등급 접두어 + 2자리 숫자: `N01, N02...`, `R01...`, `E01...`, `L01...`, `M01...`
- **어드민에서 등급 선택 시 자동 부여**(해당 등급의 다음 번호). 수동 입력 금지(중복 방지).

### 4.5 MVP 카드 목표 구성 (총 150장)

| 등급     | 장수    | 종류 배분(예시)                  |
| -------- | ------- | -------------------------------- |
| 일반 N   | 60      | 아이템 35 + 선수 25              |
| 레어 R   | 45      | 선수 30 + 마스코트 10 + 아이템 5 |
| 에픽 E   | 30      | 선수 22 + 마스코트 8             |
| 레전드 L | 12      | 선수 10 + 마스코트 2             |
| 신화 M   | 3       | 선수/마스코트 3                  |
| **합계** | **150** |                                  |

> 제작 부담 완화: 완전 신규 "원본"은 30~40종, 나머지는 색/이펙트/유니폼 변주로 확보 가능(단, 통이미지라 각 장을 개별 생성/저장).

## 5. 데이터 스키마 (확정)

> Supabase Postgres 기준. RLS로 유저별 데이터 격리.
>
> **확정됨.** 어드민 화면(2단계)을 먼저 구현해 드러난 요구를 반영했다.
> 구현은 `supabase/migrations/` 에 있다. **이 장이 기준 문서다** —
> 컬럼을 바꿔야 하면 이 장을 먼저 고치고 새 마이그레이션을 추가한다(기존 파일 수정 금지).
>
> 아래 표의 **[추가]** 표시는 화면 작업에서 드러나 초안에 없던 항목이다.

### users (Supabase Auth 확장 프로필)

| 컬럼             | 타입                   | 설명                            |
| ---------------- | ---------------------- | ------------------------------- |
| id               | uuid (PK)              | Supabase auth uid               |
| nickname         | text unique **nullable** | 닉네임. 온보딩에서 채운다     |
| favorite_team_id | int (FK teams) nullable | 응원팀. 온보딩에서 채운다      |
| points           | int                    | 보유 포인트 (기본 200)          |
| created_at       | timestamptz            |                                 |

> **`nickname` nullable 이유:** 가입 시점에는 닉네임이 없다.
> 프로필 행은 `auth.users` insert 트리거가 만들고, 앱은 `nickname is null` 이면 온보딩을 띄운다.
> 가입 보너스 200p 지급과 `point_transactions` 기록도 같은 트리거에서 처리한다.
> **운영자 계정(`app_metadata.role = 'admin'`)은 프로필을 만들지 않는다** — 게임 유저가 아니라
> 유저 목록에 섞이면 안 된다.
>
> **가입 폼이 아니라 온보딩에서 받는 이유:** 기획서 3.1 에 OAuth(구글·애플)가 있고,
> OAuth 로그인은 **가입 폼 자체가 없다.** 닉네임을 물어볼 화면이 없으므로 OAuth 유저는
> 무조건 온보딩에서 받아야 한다. 경로를 둘로 나누지 않고 온보딩 하나로 통일한다.
> 응원팀 선택도 이미 온보딩에 있어 한 흐름으로 묶인다.

#### 닉네임 규칙 (확정)

앱 온보딩에서 처음 받고, **설정에서 수정 가능**하다.

| 항목        | 규칙                                                     |
| ----------- | -------------------------------------------------------- |
| 길이        | 2~12자                                                   |
| 허용 문자   | 한글 완성형 · 영문 · 숫자 (`^[가-힣a-zA-Z0-9]+$`)        |
| 금지        | 공백 · 특수문자 · 단독 자모(`ㅋㅋㅋ`) · 이모지            |
| 유일성      | **대소문자 무시** (`Master` = `master`)                   |

- 단일 출처는 `packages/shared` 의 `nicknameSchema`. **DB 에도 같은 제약을 둔다**
  (`users_nickname_length` / `users_nickname_format` / `users_nickname_trimmed`) —
  앱이 anon key 로 직접 붙으므로 클라이언트 검증만 믿을 수 없다.
- 대소문자 무시 유일성은 `lower(nickname)` **부분 unique 인덱스**로 구현한다
  (`where nickname is not null` — 온보딩 미완료 유저가 여러 명이어도 충돌하지 않게).
- 중복 확인은 `is_nickname_available(candidate)` RPC. `users_select_own_or_admin` 정책 때문에
  유저는 자기 행만 조회할 수 있어 직접 조회로는 확인이 불가능하다.
  `security definer` 로 **boolean 만** 반환해 다른 유저의 닉네임은 노출되지 않는다.
- ⚠️ **확인과 저장 사이의 경합은 RPC 로 막을 수 없다.** unique 인덱스가 최종 방어선이며,
  앱은 unique 위반 에러를 "이미 사용 중입니다" 로 처리해야 한다.

> **`role` 컬럼을 두지 않는다(확정).** 운영자 권한은 Supabase Auth의
> `auth.users.raw_app_meta_data`(= `app_metadata`)에 `{"role":"admin"}` 으로 저장한다.
>
> 이유:
>
> - `user_metadata`는 **유저가 직접 수정할 수 있다.** 여기에 권한을 두면 아무나 스스로 admin이 될 수 있다.
>   `app_metadata`는 service role만 수정 가능하다.
> - `app_metadata`는 JWT 클레임으로 내려오므로 **RLS에서 DB 조회 없이** 판단된다.
>   `users` 컬럼으로 두면 정책마다 users를 조회해야 한다.
> - 운영자가 1명이라 "누가 운영자인지" 목록 조회가 필요 없다. 컬럼까지 두면 동기화 지점만 늘어난다.
>
> 운영자가 여러 명이 되어 목록 관리가 필요해지면 그때 `users.role` 을 추가하고
> `app_metadata` 를 권한 판단의 단일 출처로 유지한다(컬럼은 표시용 미러).

> 생성 컬럼은 쓸 수 없다 — `timestamptz - interval` 은 STABLE 이라 생성 컬럼의 IMMUTABLE 조건을 못 만족한다.
> `packages/shared` 의 `PREDICT_CLOSE_OFFSET_MINUTES` 는 **표시용**이며 이 정의를 따라간다
> (오프셋을 바꾸면 마이그레이션과 상수를 함께 고쳐야 한다).

| ---------------- | ------------------ | ----------------------------------------------- |

### 트랜잭션이 필요한 작업 (구현 시 주의)

| 작업              | 함께 처리해야 하는 것                                                                  |
| ----------------- | -------------------------------------------------------------------------------------- |
| 도감번호 부여     | count+1 방식은 동시 등록에 취약. 트랜잭션 또는 unique 제약 + 재시도                    |
| 카드 일괄 등록    | 중간 실패 시 도감번호에 구멍이 생기지 않도록 한 트랜잭션                               |
| 정산(자동·수동)   | `predictions.result` + `earned_points` 확정 → 포인트 지급 → `point_transactions` 기록   |
| 뽑기              | 포인트 차감 → 카드 지급 → 중복 환급 → `draws` + `point_transactions` 기록               |

### DB 제약으로 굳힌 불변식

문서에만 있던 규칙을 코드가 아니라 DB 제약으로 강제한다. 코드 실수로 깨질 수 없다.

| 제약                                    | 막는 것                                      |
| --------------------------------------- | -------------------------------------------- |
| `cards_dex_no_matches_grade`            | `E01` 인데 `grade=normal` 같은 접두어 불일치 |
| `cards_dex_no_format`                   | 도감번호 형식 위반                           |
| `user_cards_unique_pair`                | 중복 보유가 행으로 늘어남(count 로만 표현)   |
| `predictions_unique_per_game`           | 한 경기에 두 번 예측                         |
| `predictions_score_pair`                | 스코어 한쪽만 입력                           |
| `games_settled_has_scores`              | 정산완료인데 스코어 없음                     |
| `games_teams_differ`                    | 같은 팀끼리 경기                             |
| `draws_refund_only_when_duplicate`      | 신규 카드인데 환급 발생                      |
| `point_transactions_admin_needs_memo`   | 운영자 조정에 사유 없음                      |
| `teams_color_hex`                       | `#RRGGBB` 아닌 색상값                        |

### RLS / 권한 설계

- 쓰기 경로(뽑기·정산·포인트 지급·도감번호 부여)는 **전부 서버(service role)에서만** 수행한다.
  그래서 유저에게 `insert`/`update` 정책을 거의 주지 않는다. 예외는 `predictions` insert 뿐이며,
  **마감 전인지 DB 가 직접 확인한다**(`now() < predict_close_at`).
- **`users` 는 컬럼 단위 grant 로 제한한다.**
  ```sql
  grant update (nickname, favorite_team_id) on public.users to authenticated;
  ```
  RLS 는 컬럼을 제한하지 못한다. 테이블 전체에 update 를 주면 유저가 자기 `points` 를 올릴 수 있다.
- **`service_role` 에도 명시적 grant 가 필요하다.** "새 테이블 자동 노출" 을 껐기 때문에 새 테이블은
  어떤 role 에도 권한이 없다. service_role 은 RLS 를 우회하지만 GRANT 는 별개다.
  빠뜨리면 어드민 권한 작업과 크롤러가 전부 403 으로 실패한다
  (`20260831000003_grant_service_role.sql`).
- `anon` 에는 아무 테이블 권한도 주지 않는다. 로그인 전에는 접근할 것이 없다.

### Storage 버킷

| 버킷         | 용도        | 공개 | 크기 제한 | 쓰기    |
| ------------ | ----------- | ---- | --------- | ------- |
| `cards`      | 카드 통이미지 | O    | 5MB       | 운영자만 |
| `team-logos` | 구단 로고    | O    | 1MB       | 운영자만 |

- 둘 다 public read — 앱에서 그대로 보여주는 이미지이고 숨길 내용이 없다. CDN 캐시를 타서
  서명 URL 발급 비용도 없앤다.
- **SVG 는 허용 MIME 에서 제외**한다(스크립트 삽입 위험).
- Supabase 의 이미지 변환(on-the-fly resize)은 **Pro 플랜 전용**이므로,
  Free 에서는 **업로드 시점에 압축**해야 한다. 카드 150장을 원본 PNG 로 올리면 300~600MB 로
  Free 용량 1GB 의 절반을 넘긴다.

## 6. 포인트 경제 (확정값)

> 모든 값은 출시 후 데이터 기반 튜닝 대상. 아래는 시작값.

### 수급 (유입)

| 항목            | 포인트                                      |
| --------------- | ------------------------------------------- |
| 회원가입 보너스 | +200                                        |
| 승패 적중       | +30 / 경기                                  |
| 스코어 적중     | +150 / 경기 (승패 포함, 난이도 반영해 상향) |

### 소비

| 항목              | 포인트 |
| ----------------- | ------ |
| 일반 뽑기 1회     | -100   |
| 프리미엄 뽑기 1회 | -300   |

- 10연차: 일반 -950(할인), 프리미엄 -2850(할인) _[할인율 확정 필요, 초안]_
- 10연차 보장: 프리미엄 10연차 시 최소 1장 에픽 이상 보장 _[초안]_

### 판매/중복 환급 (등급별 고정)

| 등급     | 판매가/환급 |
| -------- | ----------- |
| 일반 N   | 5           |
| 레어 R   | 10          |
| 에픽 E   | 15          |
| 레전드 L | 20          |
| 신화 M   | 30          |

- 판매는 "중복 처리용"의 소소한 용도(뽑기 비용보다 훨씬 낮음 = 포인트가 계속 소모되게).
- 도감의 **마지막 1장은 판매 불가**(여분만 판매). 실수로 도감 비우는 것 방지.
- 자동 중복 환급 vs 수동 판매: 동일 값으로 통일.

### 뽑기 확률 (초안, 튜닝 대상)

| 등급   | 일반 뽑기 | 프리미엄 뽑기 |
| ------ | --------- | ------------- |
| 일반   | 60%       | 40%           |
| 레어   | 27%       | 33%           |
| 에픽   | 10%       | 20%           |
| 레전드 | 2.7%      | 6%            |
| 신화   | 0.3%      | 1%            |

- 등급 확정 후 그 등급 내에서 `draw_weight` 비례로 개별 카드 선택.

### 예측 상태 흐름

```
예측함(pending) → 마감(closed) → 경기중(live) → 집계중(aggregating) → 정산완료(settled)
```

- 예측 마감: 각 경기 start_at - 1시간. **서버 시각 기준**으로 판정(폰 시각 조작 방지).
- 정산: 경기 종료 감지 후(30분 간격 폴링) result·earned_points 확정, 포인트 지급.
