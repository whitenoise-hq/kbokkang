## 1. 프로젝트 개요

### 한 줄 정의

매일 열리는 KBO 경기를 승부예측하고, 맞히면 포인트를 벌어, 그 포인트로 야구 캐릭터 카드를 뽑아 도감을 채우는 개인용 모바일 앱.

### 핵심 루프

```
경기 승부예측 → 적중 시 포인트 획득 → 포인트로 카드 뽑기 → 도감 수집 → (반복)
```

### 타깃

- KBO 팬, 특히 승부예측과 수집(가챠)에 흥미가 있는 개인 유저.
- 친구 초대/대전 없이 개인이 바로 시작 가능(초기 진입장벽 최소화).

### MVP 범위

- 포함: 회원가입/로그인, 응원팀 선택, 일일 경기 승부예측, 자동 정산, 포인트, 카드 뽑기(일반/프리미엄), 도감, 중복 카드 판매.
- 제외(향후): 카드 대전(PvP), 친구 초대, 시즌/프로모션 카드(운영 단계에서 추가), 미니홈/꾸미기.

## 2. 개발 순서 (중요)

**어드민을 먼저 개발한다.** 이유: 카드 150장 규모의 데이터 관리가 필수이고, 어드민을 만들며 데이터 스키마가 확정되어 앱 개발의 기반이 된다.

**그리고 어드민 안에서는 화면(UI)을 스키마보다 먼저 만든다.**
이유: 화면을 실제로 구현해 보면 필요한 필드·상태·목록 조건이 드러나고, 그 과정에서 스키마가 바뀐다.
스키마를 먼저 확정하면 화면 작업 중에 마이그레이션을 반복해야 하므로, **화면에서 요구가 확정된 뒤 스키마를 굳힌다.**

1. **1단계** — 모노레포 기본 구조 + 공통 상수/디자인 토큰 (`packages/shared`) ✅ 완료
2. **2단계** — **어드민 화면(UI) 구현** (`01_어드민기획서.md`)
   - 목업 데이터/로컬 상태로 화면을 먼저 완성. 이 시점에는 DB에 붙이지 않는다.
   - 동시에 카드 이미지 AI 생성 작업 병행 (`03_카드프롬프트가이드.md`)
3. **3단계** — **데이터 스키마 확정 + Supabase 세팅** (본 문서 5장)
   - 2단계에서 드러난 필드·상태·조회 조건을 반영해 확정한다.
4. **4단계** — 어드민 화면을 Supabase에 연결 (목업 → 실데이터 교체, RLS·권한 적용)
5. **5단계** — 크롤링/정산 파이프라인 (GitHub Actions) 구축 및 어드민에서 검증
6. **6단계** — 앱(Expo/RN) 개발 (`02_앱기획서.md`)

> 앱(6단계) 역시 같은 원칙을 따른다: 화면 먼저, 데이터 연결은 그 다음.

| 영역           | 선택                            | 비고                                         |

| 앱(프론트)     | Expo + React Native             | 동우 주력 스택                               |
| 어드민(프론트) | React / Next.js                 | 웹, 기능 위주 단순 UI                        |
| 백엔드         | Supabase                        | DB + Auth + Storage + (필요시)Edge Functions |
| DB             | Supabase Postgres               |                                              |
| 인증           | Supabase Auth                   | 이메일/OAuth, RLS로 유저별 데이터 격리       |
| 이미지 저장    | Supabase Storage                | 카드 이미지, S3 호환 + CDN                   |
| 크롤링/정산    | **Supabase Cron + Edge Function** | 무료. pg_cron 은 플랜 제한 없음              |
| 경기 데이터    | 네이버 스포츠 `api-gw` (확정)   | 결과는 전 유저 공통, 서버에서 1회만 수집     |
| 어드민 배포    | Vercel (Hobby)                  | 레포 public 이라 Git 연동 무료               |
| 레포 구조      | 모노레포 (Turborepo + pnpm)     | 앱·어드민이 스키마/상수 공유                 |
| 앱 디자인      | 자체 토큰 (토스 스타일)         | `04_앱디자인가이드.md` 기준. 토큰은 `packages/shared/theme.ts` |
| 어드민 UI      | shadcn/ui + Tailwind            | 디자인 가이드 대상 아님. primary만 브랜드 컬러 공유 |

### 레포 구조 (모노레포)

- 레포명: **kbokkang** (GitHub kebab-case)
- npm 스코프: `@kbokkang/*`

```
kbokkang/                    (Turborepo + pnpm)
├─ apps/
│  ├─ mobile/                (Expo + React Native — 앱, @kbokkang/mobile)
│  ├─ admin/                 (Next.js — 어드민, @kbokkang/admin)
├─ packages/
│  ├─ shared/                (@kbokkang/shared — Supabase 타입, 포인트 상수, 등급/카드 정의, 확률 테이블, 디자인 토큰)
│  └─ assets/                (@kbokkang/assets — 앱·어드민 공용 정적 파일. 폰트 등)
│     └─ fonts/pretendard/   (web/*.woff2 = 어드민 / native/*.otf = 앱 / LICENSE.txt)
│  └─ crawler/               (@kbokkang/crawler — 껍데기 CLI + 테스트. 로직은 supabase/functions/_shared)
├─ docs/                     (기획서)
└─ CLAUDE.md
```

- **공통 코드는 반드시 `packages/shared`에 단일 정의.** 포인트 값·확률·등급·판매가를 앱/어드민에 중복 정의 금지(불일치 사고 방지).
- **공용 폰트/이미지 파일은 `packages/assets`에 보관.** 앱·어드민에 각각 복사해두지 않는다.
  - Pretendard는 npm 패키지(`pretendard`) 설치하지 않는다: 설치 용량 97MB이고 RN은 node_modules의 폰트를 못 쓴다. 필요한 3굵기 파일만 직접 보관(총 약 5.3MB).
  - 웹은 `.woff2`, React Native는 `.otf`/`.ttf`만 가능 → 포맷별로 `web/`, `native/` 분리.
- **크롤러는 모노레포 안에 둔다**(`apps/crawler`). `packages/shared` 의 팀 코드·상태 매핑을 앱·어드민과 공유해야 하므로 분리 레포는 손해다.
- **레포는 public.** 비공개 조직 레포는 Vercel Git 연동이 Pro(유료)라서 전환했다. 시크릿은 전부 gitignore·Actions Secrets 에 있고 커밋 이력에 올라간 적 없다.
  - 대신 스키마·RLS 정책·뽑기 확률이 공개된다. 앱이 anon key 로 직접 붙는 구조라 **RLS 가 유일한 방어선**이고, 이제 공격자가 그 내용을 읽을 수 있다는 뜻이다.
  - Actions 워크플로 트리거는 `schedule` + `workflow_dispatch` 만 둔다. `pull_request` 를 추가하면 외부인이 PR 로 시크릿을 빼갈 수 있다.

### 크롤링/정산 정책

- **경기 시간대에만 30분 간격**으로 실행. 그 외 시간/경기 없는 날은 미실행.
- **실시간 정산 아님(지연 정산 허용).** 유저에겐 "집계 중" 상태로 표시.
- 적응형: 안 끝난 경기만 확인. 모든 경기 정산 완료 시 그날 작업 종료.
- 경기 결과는 모든 유저에게 동일 → 서버가 1회 수집 후 DB 저장, 앱은 읽기만. 유저 수 증가와 크롤링 비용 무관.
- GitHub Actions cron은 실행 시각이 정확하지 않을 수 있음(수 분 지연 가능) → 지연 정산이라 문제없음.

#### 액션 구성 (확정)

실행 주체는 **Supabase Cron(pg_cron)** 이고, 로직은 **Edge Function** 이다.
GitHub Actions 는 수동 복구(`workflow_dispatch`) 전용으로만 남겼다 — 이유는 아래.

| 잡 | cron (UTC) | KST | 범위 |
| -- | ---------- | --- | ---- |
| `kbo-schedule` | `0 0 * * 1` | 월 09:00 | **기준일 포함 7일**(월~일) |
| `kbo-settle` | `0,30 0-16 * * *` | 매일 09:00~01:00, 30분 간격 | **최근 3일** upsert + 정산 |

⚠️ **pg_cron 은 UTC 로 동작한다.** KST 로 착각하면 9시간 어긋난다.

#### 게이트 — cron 은 고정, 판단은 코드가 한다

cron 은 하루 34회 고정으로 돌지만, **실제로 소스를 부르는 건 의미 있는 시각뿐**이다
(`supabase/functions/_shared/gate.ts`). 통과 조건 — 하나라도 맞으면 일한다:

1. **오늘(KST) 안에 성공 실행이 없었다** — 하루 첫 실행. 일정 수집 + 어제 미정산 복구.
   - ⚠️ `crawl_runs.target_date` 가 아니라 **`run_at`** 으로 판정한다. 주간 일정 잡이 7일치
     행을 미리 쓰기 때문에 `target_date` 로 보면 "오늘 기록 없음"이 성립하지 않는다.
2. **창 안에 미정산 경기가 있고, 그중 하나가 시작 1시간 전을 지났다**
   - 1시간 전부터 우천 취소·시각 변경이 확정되고, 시작 후에는 결과가 나온다
   - 1시간 = 예측 마감 시점(`games.predict_close_at`)과 같은 기준

결과: 하루 소스 호출 **~7회**, 정산 지연 **30분 이내**.

판단을 cron 에 두지 않은 이유: 동적으로 cron 을 다시 등록하면 상태가 cron 테이블에 생긴다.
등록이 실패하면 그날 정산이 아예 안 돌고, 해제가 실패하면 계속 돈다. 게이트는 상태가 없고
테스트할 수 있으며, 잘못 판단해도 다음 실행이 다시 판단한다.

#### pg_cron 실측 결과

09-03 하루 동안 **30분마다 정확히 발화**했다(`16:30:00.116`, `15:30:00.179` …). 결번 0, 지연 0.
`cron.job_run_details` 전건 `succeeded`. 이전 판단은 옳았다.

⚠️ 다만 **pg_net 은 비동기라 HTTP 실패가 조용하다.** cron 이 성공으로 기록돼도 함수가
500 을 반환했을 수 있다(09-03 에 그랬다). 그래서 **실패를 `crawl_runs` 에 남기는 것이 필수**다.
진단은 `net._http_response` 의 `status_code` 로 한다.

#### ⚠️ GitHub Actions schedule 은 왜 버렸나 (실측)

| 날짜 | cron | 예정 | 실제 실행 |
| ---- | ---- | ---- | --------- |
| 09-01 | `0,30` (정시) | ~30회 | **2회** (하나는 18분 지연) |
| 09-02 | `7,37` (정시 회피) | ~30회 | **4회** (하나는 3시간 19분 지연) |

분을 정시에서 옮겨도 4회였다. 실행 간격이 5.5h → 4h → 3.6h 로 거의 균일해서, 무작위 드롭이
아니라 **레포당 스케줄 실행이 조절되는 패턴**으로 보인다(GitHub 이 이유를 노출하지 않으므로 추론).

결과: 09-02 경기(18:30 시작, 21:40 종료 추정)가 **09-03 00:16 에 정산**됐다 — 2시간 30분 지연.

설정 문제가 아니었다: 워크플로 `active`, Actions 레포·조직 양쪽 활성, public 레포라 쿼터 무관,
실행된 건은 전부 성공. GitHub 이 나머지를 **아예 만들지 않았다.**

> "If the load is sufficiently high enough, some queued jobs **may be dropped**.
> High load times include **the start of every hour**." — GitHub Docs

#### Vault 등록 (선행 조건, 사람이 한 번)

pg_cron 이 Edge Function 을 부를 때 service role key 가 필요하다. **키를 마이그레이션에
넣지 않는다**(public 레포). Vault 에 넣고 `crawler.invoke()` 가 읽는다.

Supabase SQL 에디터에서 한 번 실행한다:

```sql
select vault.create_secret(
  '<service role key>',       -- Project Settings > API Keys
  'service_role_key',
  'pg_cron 이 Edge Function 을 호출할 때 쓰는 키'
);
```

이미 있으면 `vault.update_secret` 을 쓴다. 등록 확인:

```sql
select name, created_at from vault.secrets where name = 'service_role_key';
select jobname, schedule, active from cron.job;
```

⚠️ **service role key 형식이 두 가지다.** Supabase 가 키 체계를 이전 중이라 한 프로젝트에
공존한다 — Edge Function 에 주입되는 값은 신규 `sb_secret_...`(41자), 어드민 `.env` 는
레거시 JWT `eyJ...`(219자). 함수의 인증 가드는 **두 형식을 모두 받는다**(주입값 일치 또는
JWT `role` 클레임). Vault 에는 어느 쪽을 넣어도 된다.

- 일정 수집이 **실행일(월)을 포함**하는 이유: 월요일도 개막 주·시즌 막바지엔 경기가 있다
  (2026 실측 3/16, 3/23, 10/5). 화요일부터 받으면 그 월요일 경기가 누락된다.
- 정산 액션이 매일 오늘 경기를 upsert 하므로 **일정 액션 실패는 치명적이지 않다.**
  우천 취소·시작 시각 변경도 이 경로로 30분 안에 반영된다.
- 수동 복구 경로 두 가지. **이게 없으면 경기마다 수동 정산뿐이다.**
  - Edge Function 직접 호출: `{"date":"2026-09-01","force":true}` POST (게이트 무시)
  - GitHub Actions `workflow_dispatch` (로그 보기 편하다. CLI 는 항상 force)

#### ⚠️ GitHub Actions schedule 은 보장이 아니다 (실측)

2026-09-01, 예정된 약 30회 중 **2회만 실행됐다**(하나는 18분 지연). 설정 문제가 아니었다 —
워크플로는 `active`, Actions 는 레포·조직 양쪽 활성, public 레포라 쿼터도 무관, 실행된 2건은 성공.
GitHub 이 나머지를 **아예 만들지 않았다.**

> "If the load is sufficiently high enough, some queued jobs **may be dropped**.
> High load times include **the start of every hour**." — GitHub Docs

대응은 두 겹이다:

1. **cron 분을 정시에서 옮긴다**(`0,30` → `7,37`). 확률을 줄이는 것뿐이고 보장은 아니다.
2. **정산 잡이 최근 3일을 훑어 자기복구한다** ← 진짜 방어선.
   실행이 빠져도 다음 실행이 주워간다. 지연 정산 정책이 이 지연을 허용한다.

하루만 보던 시절 9/1 5경기가 `live` 로 멈춰 영구 미정산이 됐다. 다음 실행은 이미 날짜가
바뀌어 9/2 를 보고 있었다. **cron 창이 KST 자정을 넘어가도 어제가 범위 안이면 문제없다.**

소스가 기간 조회를 지원하므로 3일치도 HTTP 요청 한 번이다. 창 안이 전부 정산 완료면
소스를 부르지 않고 즉시 끝난다.

**대안: Supabase Cron (pg_cron) — 무료.** Postgres 익스텐션이라 플랜 제한이 없고
최소 간격 1초, Edge Functions 무료 한도 월 50만 회(필요량 ~900회). 큐 대기·드롭이 없어
타이밍이 정확하다. 단 크롤러를 **Edge Function(Deno)으로 이식**해야 한다.
자기복구가 먼저 있어야 이전이 안전하다 — 새 플랫폼에서 장애가 나도 영구 미정산이 되지 않는다.

#### 데이터 소스 — 네이버 스포츠 `api-gw` (확정)

`https://api-gw.sports.naver.com/schedule/games?upperCategoryId=kbaseball&fromDate=&toDate=`

조사 결과 (전부 실제 HTTP 확인):

| 후보 | 결론 |
| ---- | ---- |
| KBO 공식 | robots.txt 가 모든 데이터 경로 차단 → 제외 |
| TheSportsDB 무료 | 하루 5경기 중 3경기만 내려옴 → 제외 |
| statiz | 일정 조회에 로그인 필요 → 제외 |
| flashscore | 결과 경로는 허용이나 비문서 `¬`/`÷` 구분자 포맷 → 제외 |
| **네이버 api-gw** | robots.txt 없음, 헤더 불필요, 깔끔한 JSON 3.9KB → **채택** |

- **폴백 없음.** 검증 안 된 폴백은 썩고, 수동 정산 UI 가 이미 있으며 지연 정산 정책이 완충이다.
- ⚠️ 문서화된 공개 API 가 아니다. 응답 구조가 예고 없이 바뀔 수 있다.

#### 소스 신뢰 방침 (중요)

2026 시즌 843경기 표본으로 규칙을 확인했다. 코드는 `supabase/functions/_shared/kbo-source.ts`.

**로직은 한 벌만 둔다.** Edge Function(Deno)과 로컬 CLI(`apps/crawler`, Node)가 같은 파일을
임포트한다. `_shared` 는 플랫폼 무관(설정을 인자로 받는다), `_runtime` 은 Deno 전용이다.

- 응답을 zod 로 검증하고 구조가 어긋나면 **실패시킨다.** 스코어가 전부 0 으로 들어가는 것보다
  안 들어오는 게 낫다.
- **승패는 소스의 `winner` 필드를 쓰지 않고 스코어로 직접 판정한다.**
- **취소 경기는 0:0 으로 내려온다** → 스코어를 null 로 남겨 "결과 없음"과 구분한다.
  (전체의 약 8%가 우천 취소)
- **정규시즌만 수집.** 3중 필터: `categoryId === 'kbo'` → 10개 구단 화이트리스트 → 경기 ID 패턴.
  - 올스타전은 팀 코드가 `EA`(드림) / `WE`(나눔), 경기 ID 연도 자리가 `9999`.
  - 시범경기는 `kbaseballetc` 카테고리라 애초에 안 들어온다.
  - ⚠️ **포스트시즌은 팀 코드가 정규와 같아 화이트리스트로 못 걸러낸다.** 아직 피드에 없지만
    등장하면 섞인다. ID 패턴 불일치 로그가 감시 장치다.
- `SK` 는 SSG 의 레거시 코드다. 소스가 아직 이걸 쓴다.
- 소스 `gameDateTime` 에 **타임존 표기가 없다.** KST 로 해석해야 한다(UTC 로 읽으면 9시간 밀림).

#### 멱등성

- `games.external_id` 가 upsert 키다. 30분마다 같은 경기를 다시 받으므로 이게 없으면 중복이 쌓인다.
- **이미 정산된 경기는 덮어쓰지 않는다** — 지급한 포인트와 어긋난다.

#### 우천 취소 (`games.cancelled`)

취소 경기는 `status = 'settled'`(더 이상 처리할 것 없음) + `cancelled = true` + 스코어 null 이다.
`cancelled` 컬럼이 5장에 추가됐다 — 원래 기획서가 "취소 여부는 별도로 표시한다"고 했던 그것이다.

⚠️ **이 표시가 없으면 배치 전체가 죽는다.** `games_settled_has_scores` 가 settled 에 스코어를
요구하므로 취소 경기가 제약을 위반하고, upsert 가 한 배치로 나가기 때문에 **취소 1건이 그날
전체를 막는다.** 2026-09-03 에 실제로 그랬고 정상 종료된 4경기도 미정산으로 남았다.

제약은 이렇게 바뀌었다 — 정상 경기는 여전히 스코어를 요구한다:

```sql
check (status <> 'settled' or cancelled or (home_score is not null and away_score is not null))
check (not cancelled or (home_score is null and away_score is null))
```

**취소 경기의 예측은 `void`(무효)로 자동 마감된다.**

- `prediction_result` enum 에 `'void'` 추가. `earned_points = 0` 으로 마감한다.
- **DB 트리거**(`void_cancelled_predictions`)가 처리한다 — 크롤러 코드에 두면 다른 경로로
  취소된 경기가 누락된다. 데이터의 불변식이므로 트리거로 강제한다.
- 마감하지 않으면 `pending` 으로 남아 유저 화면에 "집계 중"이 영원히 표시된다.
- `settle_game()` 은 취소 경기를 거부한다(스코어 없는 경기에 결과를 넣는 것 차단).
- **통계에서 제외한다:** 최고 연승은 `void` 로 끊기지 않고(유저 탓이 아니다),
  적중률 분모는 `resolvedPredictions`(pending·void 제외)를 쓴다.

검증: 트리거 동작을 임시 RPC 로 확인했다(`result=void earned_points=0`).
테스트 데이터는 예외를 던져 전부 롤백했다. 앱(6단계)에서 실유저로 재확인할 것.

## 4. 카드 시스템 (공통 규칙)

### 4.1 등급 (5단계)

| 등급   | 코드(도감 접두어) | 색 규칙         | 레이아웃 | 반짝임 모션 |
| ------ | ----------------- | --------------- | -------- | ----------- |
| 일반   | N (Normal)        | 회색            | 박스형   | 없음        |
| 레어   | R (Rare)          | 파랑            | 박스형   | 없음        |
| 에픽   | E (Epic)          | 보라            | 박스형   | 없음        |
| 레전드 | L (Legend)        | 금              | 풀아트   | 있음        |
| 신화   | M (Mythic)        | 빨강(홀로 가미) | 풀아트   | 있음        |

- **박스형**: 캐릭터/사물이 카드 안 네모 영역에 담긴 형태(포켓몬 일반 카드 스타일).
- **풀아트**: 일러스트가 카드 전체를 채우는 형태(포켓몬 SAR 스타일).
- 반짝임 모션: 레전드/신화만. 이미지가 아니라 **앱에서 코드로** 이미지 위에 얹음.
- **등급색 실제 hex 값은 `04_앱디자인가이드.md` 1장이 단일 출처**(코드에서는 `@kbokkang/shared`의 `CARD_GRADE_META.color`). 등급색은 카드·등급 표시 전용이며 일반 UI에 남용 금지.

### 4.2 카드 종류

- **선수** (오리지널 가상 캐릭터, 특정 실존 선수 아님)
- **마스코트** (오리지널 동물 캐릭터, 특정 구단 마스코트 아님)
- **아이템** (야구 장비·응원 용품)

### 4.3 카드 이미지 원칙

- **통이미지**: 카드 1장 = 완성된 이미지 1장. 앱은 이미지 URL 하나만 호출.
- 프레임·등급 표현까지 이미지에 포함(AI 생성 시).
- **텍스트(카드 이름/등급/도감번호)는 이미지에 넣지 않음.** 앱에서 코드로 표시.
  (AI 한글 깨짐 방지 + 수정 자유 + 다국어 대응)
- IP 주의: 실존 선수·구단 로고·유니폼 디자인을 카드에 사용 금지(오리지널만).
  - 단, 응원팀 선택 화면의 구단 로고는 별도(동우 판단하에 DB에 저장해 사용 — 리스크 인지 상태).

### 4.4 도감 번호

- 등급 접두어 + 2자리 숫자: `N01, N02...`, `R01...`, `E01...`, `L01...`, `M01...`
- **어드민에서 등급 선택 시 자동 부여**(해당 등급의 다음 번호). 수동 입력 금지(중복 방지).

### 4.5 MVP 카드 목표 구성 (총 150장)

| 등급     | 장수    | 종류 배분(예시)                  |

## 5. 데이터 스키마 (확정)

> Supabase Postgres 기준. RLS로 유저별 데이터 격리.
>
> **확정됨.** 어드민 화면(2단계)을 먼저 구현해 드러난 요구를 반영했다.
> 구현은 `supabase/migrations/` 에 있다. **이 장이 기준 문서다** —
> 컬럼을 바꿔야 하면 이 장을 먼저 고치고 새 마이그레이션을 추가한다(기존 파일 수정 금지).
>
> 아래 표의 **[추가]** 표시는 화면 작업에서 드러나 초안에 없던 항목이다.

### users (Supabase Auth 확장 프로필)

| 컬럼             | 타입                   | 설명                            |
| ---------------- | ---------------------- | ------------------------------- |
| id               | uuid (PK)              | Supabase auth uid               |
| nickname         | text unique **nullable** | 닉네임. 온보딩에서 채운다     |
| favorite_team_id | int (FK teams) nullable | 응원팀. 온보딩에서 채운다      |
| points           | int                    | 보유 포인트 (기본 200)          |
| created_at       | timestamptz            |                                 |

> **`nickname` nullable 이유:** 가입 시점에는 닉네임이 없다.
> 프로필 행은 `auth.users` insert 트리거가 만들고, 앱은 `nickname is null` 이면 온보딩을 띄운다.
> 가입 보너스 200p 지급과 `point_transactions` 기록도 같은 트리거에서 처리한다.
> **운영자 계정(`app_metadata.role = 'admin'`)은 프로필을 만들지 않는다** — 게임 유저가 아니라
> 유저 목록에 섞이면 안 된다.
>
> **가입 폼이 아니라 온보딩에서 받는 이유:** 기획서 3.1 에 OAuth(구글·애플)가 있고,
> OAuth 로그인은 **가입 폼 자체가 없다.** 닉네임을 물어볼 화면이 없으므로 OAuth 유저는
> 무조건 온보딩에서 받아야 한다. 경로를 둘로 나누지 않고 온보딩 하나로 통일한다.
> 응원팀 선택도 이미 온보딩에 있어 한 흐름으로 묶인다.

#### 닉네임 규칙 (확정)

앱 온보딩에서 처음 받고, **설정에서 수정 가능**하다.

| 항목        | 규칙                                                     |
| ----------- | -------------------------------------------------------- |
| 길이        | 2~12자                                                   |
| 허용 문자   | 한글 완성형 · 영문 · 숫자 (`^[가-힣a-zA-Z0-9]+$`)        |
| 금지        | 공백 · 특수문자 · 단독 자모(`ㅋㅋㅋ`) · 이모지            |
| 유일성      | **대소문자 무시** (`Master` = `master`)                   |

- 단일 출처는 `packages/shared` 의 `nicknameSchema`. **DB 에도 같은 제약을 둔다**
  (`users_nickname_length` / `users_nickname_format` / `users_nickname_trimmed`) —
  앱이 anon key 로 직접 붙으므로 클라이언트 검증만 믿을 수 없다.
- 대소문자 무시 유일성은 `lower(nickname)` **부분 unique 인덱스**로 구현한다
  (`where nickname is not null` — 온보딩 미완료 유저가 여러 명이어도 충돌하지 않게).
- 중복 확인은 `is_nickname_available(candidate)` RPC. `users_select_own_or_admin` 정책 때문에
  유저는 자기 행만 조회할 수 있어 직접 조회로는 확인이 불가능하다.
  `security definer` 로 **boolean 만** 반환해 다른 유저의 닉네임은 노출되지 않는다.
- ⚠️ **확인과 저장 사이의 경합은 RPC 로 막을 수 없다.** unique 인덱스가 최종 방어선이며,
  앱은 unique 위반 에러를 "이미 사용 중입니다" 로 처리해야 한다.

> **`role` 컬럼을 두지 않는다(확정).** 운영자 권한은 Supabase Auth의
> `auth.users.raw_app_meta_data`(= `app_metadata`)에 `{"role":"admin"}` 으로 저장한다.
>
> 이유:
>
> - `user_metadata`는 **유저가 직접 수정할 수 있다.** 여기에 권한을 두면 아무나 스스로 admin이 될 수 있다.
>   `app_metadata`는 service role만 수정 가능하다.
> - `app_metadata`는 JWT 클레임으로 내려오므로 **RLS에서 DB 조회 없이** 판단된다.
>   `users` 컬럼으로 두면 정책마다 users를 조회해야 한다.
> - 운영자가 1명이라 "누가 운영자인지" 목록 조회가 필요 없다. 컬럼까지 두면 동기화 지점만 늘어난다.
>
> 운영자가 여러 명이 되어 목록 관리가 필요해지면 그때 `users.role` 을 추가하고
> `app_metadata` 를 권한 판단의 단일 출처로 유지한다(컬럼은 표시용 미러).

> 판매가/환급가는 카드에 저장하지 않음. 등급 기준 상수(6장 이하 참조)로 계산.

> **`image_url` nullable 확정**: 어드민에서 이미지 없이 먼저 등록하는 흐름이 필요하다.
> 참조 형식(Storage 공개 URL vs 버킷 경로)은 Storage 연결 시 확정한다.
>
> **`deleted_at` 추가**: 삭제는 soft delete만 한다(보유자와의 정합성).
> 조회는 기본 `deleted_at IS NULL`. 뽑기 대상에서도 제외한다.
> 삭제·등급변경으로 비워진 도감번호는 **재사용하지 않는다.**

### games (경기)

| 컬럼             | 타입                 | 설명                                      |
| ---------------- | -------------------- | ----------------------------------------- |
| id               | uuid (PK)            |                                           |
| external_id      | **[추가]** text unique nullable | 원본(크롤링 소스)의 경기 ID     |
| game_date        | date                 | 경기 날짜                                 |
| start_at         | timestamptz          | 경기 시작 시각                            |
| predict_close_at | timestamptz          | 예측 마감(=start_at - 1h). **DB 트리거가 설정** |
| home_team_id     | int (FK)             |                                           |
| away_team_id     | int (FK)             |                                           |
| status           | enum                 | scheduled/closed/live/aggregating/settled |
| home_score       | int nullable         | 결과                                      |
| away_score       | int nullable         | 결과                                      |
| settled_at       | timestamptz nullable | 정산 완료 시각                            |

> **`external_id` 추가 이유 — 크롤링 멱등성.** 크론이 30분마다 같은 경기를 다시 수집하므로
> 중복 삽입을 막을 자연키가 필요하다. `(날짜, 홈, 원정)` 조합은 **더블헤더**에서 깨지고,
> `start_at` 을 포함하면 우천 지연으로 시작 시각이 바뀔 때 중복이 생긴다.
> 원본 경기 ID 로 upsert 하는 것이 유일하게 안전하다. 수동 등록 경기는 null 허용.
>
> **`predict_close_at` 은 DB 트리거가 설정한다**(`start_at - interval '1 hour'`).
> 크롤러가 계산해 넣으면 틀릴 수 있고, 마감 판정은 서버 시각 기준이라 DB 가 보장하는 게 안전하다.
> 생성 컬럼은 쓸 수 없다 — `timestamptz - interval` 은 STABLE 이라 생성 컬럼의 IMMUTABLE 조건을 못 만족한다.
> `packages/shared` 의 `PREDICT_CLOSE_OFFSET_MINUTES` 는 **표시용**이며 이 정의를 따라간다
> (오프셋을 바꾸면 마이그레이션과 상수를 함께 고쳐야 한다).

### crawl_runs (크롤링 실행 이력) — **도입 확정**

어드민의 "크롤링 상태 확인"(01 문서 3.5)을 제대로 하려면 **마지막 수집 시각과 성공 여부**가
필요하다. 이 테이블이 없으면 "크롤링이 아예 안 돌았는지"와 "경기가 없는 날인지"를 구분할 수 없다.

| 컬럼          | 타입          | 설명                          |
| ------------- | ------------- | ----------------------------- |
| id            | uuid (PK)     |                               |
| target_date   | date          | 수집 대상 경기 날짜           |
| run_at        | timestamptz   | 실행 시각                     |
| success       | bool          | 성공 여부                     |
| games_found   | int           | 수집한 경기 수                |
| games_settled | int           | 이번 실행에서 정산한 경기 수  |
| error         | text nullable | 실패 사유                     |

> 조회는 운영자만. 쓰기는 크롤러(service role)만.

⚠️ **`target_date` 는 "이 날짜의 데이터를 수집했다"는 뜻이다. 여러 날짜를 수집했으면 날짜마다
한 행을 남겨야 한다.** 일정 액션이 7일치를 받고 시작일 한 행만 남겼더니, 나머지 6일은 경기가
들어와 있는데도 어드민 배너가 "수집 이력 없음"으로 표시됐다.

**경기 0건인 날짜도 행을 남긴다.** 그게 "경기 없는 날"의 증거다 — 행이 없으면 미실행과 구분이 안 된다.

### 파생/집계 값 (컬럼 아님)

화면에 필요하지만 테이블 컬럼이 아닌 것들. 뷰 또는 조인 집계로 제공한다.

| 값               | 쓰이는 곳          | 계산                                            |
| ---------------- | ------------------ | ----------------------------------------------- |
| 도감 진행률      | 유저 목록/상세     | `user_cards` distinct card_id / 전체 카드 종수  |
| 등급별 도감 진행 | 유저 상세          | 위를 등급별로                                   |
| 예측 분포        | 경기 목록/상세     | `predictions` 집계 (홈/원정 선택 수)            |
| 카드 보유 현황   | 통계               | `user_cards` 카드별 보유자 수·총 발급 장수      |

### 트랜잭션이 필요한 작업

| 작업            | 함께 처리해야 하는 것                                                                | 구현                            |
| --------------- | ------------------------------------------------------------------------------------ | ------------------------------- |
| 도감번호 부여   | count+1 은 동시 등록에 취약 → unique 제약 + 재시도(최대 5회)                          | ✅ 어드민 Repository            |
| 카드 일괄 등록  | 중간 실패 시 도감번호에 구멍이 생기지 않도록 한 트랜잭션                              | ✅ `create_cards_bulk()` RPC    |
| 정산(자동·수동) | `predictions.result` + `earned_points` 확정 → 포인트 지급 → `point_transactions` 기록 | ✅ `settle_game()` RPC          |
| 뽑기            | 포인트 차감 → 카드 지급 → 중복 환급 → `draws` + `point_transactions` 기록              | ⬜ 앱(6단계)에서 RPC 로 구현    |

- `settle_game()` 은 **자동(크롤러)·수동(어드민) 정산이 함께 쓴다.** 규칙이 두 곳으로 갈라지면
  결과가 달라진다.
- `create_cards_bulk()` 은 `lock table cards in exclusive mode` 로 동시 등록을 직렬화한다
  (EXCLUSIVE 는 SELECT 를 막지 않는다).
- **무승부 처리:** 승패 예측은 홈/원정 중 하나를 고르는 방식이므로, 무승부면 전원 미적중이다.

### 집계 뷰 (PostgREST 는 GROUP BY 를 못 한다)

| 뷰                 | 용도                          |
| ------------------ | ----------------------------- |
| `user_summaries`   | 유저 목록 + 도감 진행률       |
| `games_with_stats` | 경기 + 예측 분포              |
| `card_spreads`     | 카드별 보유자 수·발급 장수    |
| `draw_grade_stats` | 등급별 실제 뽑기 분포         |
| `point_flow_daily` | 일별 포인트 유입/소비(KST)    |

- 전부 **`security_invoker = true`**. 기본값은 뷰 소유자 권한으로 동작해 **RLS 를 우회**하므로
  반드시 명시해야 한다.
- ⚠️ **뷰를 추가하면 조인 타입 추론이 깨질 수 있다.** PostgREST 는 뷰에도 하위 테이블의 FK 관계를
  물려주므로, `card_spreads.card_id` 때문에 `user_cards.card_id` 의 조인 대상이
  `cards`/`card_spreads` 로 모호해져 supabase-js 가 to-one 조인을 배열로 추론한다.
  어드민에서는 `one()` 헬퍼로 흡수한다.

### 클라이언트 타입 (필수)

```ts
createServerClient<Database>(...)   // 제네릭이 없으면 모든 쿼리 결과가 any 가 된다
```

타입만 생성해두고 제네릭을 빼먹으면 **컬럼명 오타도 통과한다.** 실제로 그 상태로 한동안
작업했다. 타입 생성 후에는 잘못된 컬럼명으로 에러가 나는지 한 번 확인할 것.

재생성:

```bash
supabase gen types typescript --linked --schema public > packages/shared/src/database.types.ts
```

`packages/shared/src/db-consistency.ts` 가 손으로 쓴 상수(`CARD_GRADES` 등)와 DB enum 이
어긋나면 컴파일을 깨뜨린다. 마이그레이션에서 enum 을 바꾸면 여기서 잡힌다.

### DB 제약으로 굳힌 불변식

문서에만 있던 규칙을 코드가 아니라 DB 제약으로 강제한다. 코드 실수로 깨질 수 없다.

| 제약                                    | 막는 것                                      |
| --------------------------------------- | -------------------------------------------- |
| `cards_dex_no_matches_grade`            | `E01` 인데 `grade=normal` 같은 접두어 불일치 |
| `cards_dex_no_format`                   | 도감번호 형식 위반                           |
| `user_cards_unique_pair`                | 중복 보유가 행으로 늘어남(count 로만 표현)   |
| `predictions_unique_per_game`           | 한 경기에 두 번 예측                         |
| `predictions_score_pair`                | 스코어 한쪽만 입력                           |
| `games_settled_has_scores`              | 정산완료인데 스코어 없음                     |
| `games_teams_differ`                    | 같은 팀끼리 경기                             |
| `draws_refund_only_when_duplicate`      | 신규 카드인데 환급 발생                      |
| `point_transactions_admin_needs_memo`   | 운영자 조정에 사유 없음                      |
| `teams_color_hex`                       | `#RRGGBB` 아닌 색상값                        |

### RLS / 권한 설계

- 쓰기 경로(뽑기·정산·포인트 지급·도감번호 부여)는 **전부 서버(service role)에서만** 수행한다.
  그래서 유저에게 `insert`/`update` 정책을 거의 주지 않는다. 예외는 `predictions` insert 뿐이며,
  **마감 전인지 DB 가 직접 확인한다**(`now() < predict_close_at`).
- **`users` 는 컬럼 단위 grant 로 제한한다.**
  ```sql
  grant update (nickname, favorite_team_id) on public.users to authenticated;
  ```
  RLS 는 컬럼을 제한하지 못한다. 테이블 전체에 update 를 주면 유저가 자기 `points` 를 올릴 수 있다.
- **`service_role` 에도 명시적 grant 가 필요하다.** "새 테이블 자동 노출" 을 껐기 때문에 새 테이블은
  어떤 role 에도 권한이 없다. service_role 은 RLS 를 우회하지만 GRANT 는 별개다.
  빠뜨리면 어드민 권한 작업과 크롤러가 전부 403 으로 실패한다
  (`20260831000003_grant_service_role.sql`).
- `anon` 에는 아무 테이블 권한도 주지 않는다. 로그인 전에는 접근할 것이 없다.

### Storage 버킷

| 버킷         | 용도        | 공개 | 크기 제한 | 쓰기    |
| ------------ | ----------- | ---- | --------- | ------- |
| `cards`      | 카드 통이미지 | O    | 5MB       | 운영자만 |

## 6. 포인트 경제 (확정값)

> 모든 값은 출시 후 데이터 기반 튜닝 대상. 아래는 시작값.

> **예측은 무료다.** 포인트를 걸지 않는다. 맞히면 받고 틀리면 0이다.
> 그래서 경기 취소 시 **환급 대상이 없다** — 예측을 `void`(무효)로 마감만 한다.
> 베팅 방식으로 바꾸려면 스키마·정산·환급·뽑기 비용 균형을 모두 재설계해야 한다.

### 수급 (유입)

| 항목            | 포인트                                      |
| --------------- | ------------------------------------------- |
| 회원가입 보너스 | +200                                        |
| 승패 적중       | +30 / 경기                                  |
| 스코어 적중     | +150 / 경기 (승패 포함, 난이도 반영해 상향) |

### 소비

| 항목              | 포인트 |
| ----------------- | ------ |
| 일반 뽑기 1회     | -100   |
| 프리미엄 뽑기 1회 | -300   |

- 10연차: 일반 -950(할인), 프리미엄 -2850(할인) _[할인율 확정 필요, 초안]_
- 10연차 보장: 프리미엄 10연차 시 최소 1장 에픽 이상 보장 _[초안]_

### 판매/중복 환급 (등급별 고정)

| 등급     | 판매가/환급 |
| -------- | ----------- |
| 일반 N   | 5           |
| 레어 R   | 10          |
| 에픽 E   | 15          |
| 레전드 L | 20          |
| 신화 M   | 30          |

- 판매는 "중복 처리용"의 소소한 용도(뽑기 비용보다 훨씬 낮음 = 포인트가 계속 소모되게).
- 도감의 **마지막 1장은 판매 불가**(여분만 판매). 실수로 도감 비우는 것 방지.
- 자동 중복 환급 vs 수동 판매: 동일 값으로 통일.

### 뽑기 확률 (초안, 튜닝 대상)

| 등급   | 일반 뽑기 | 프리미엄 뽑기 |
| ------ | --------- | ------------- |
| 일반   | 60%       | 40%           |
| 레어   | 27%       | 33%           |
| 에픽   | 10%       | 20%           |
| 레전드 | 2.7%      | 6%            |
| 신화   | 0.3%      | 1%            |

- 등급 확정 후 그 등급 내에서 `draw_weight` 비례로 개별 카드 선택.

### 예측 상태 흐름

```
예측함(pending) → 마감(closed) → 경기중(live) → 집계중(aggregating) → 정산완료(settled)
```

- 예측 마감: 각 경기 start_at - 1시간. **서버 시각 기준**으로 판정(폰 시각 조작 방지).
- 정산: 경기 종료 감지 후(30분 간격 폴링) result·earned_points 확정, 포인트 지급.

## 7. 향후 과제 (MVP 이후)

- 카드 대전(PvP): 능력치 + 비동기 대전 우선 검토(실시간 서버·밸런싱 부담 큼).
- 시즌 카드 / 프로모션 카드: 프로야구 행사·기념일마다 어드민에서 발급, 뽑기 유도.
- 친구 초대 / 그룹 랭킹.
- 카드 제작: 목표 150장까지 시즌 업데이트로 점진 확장.
