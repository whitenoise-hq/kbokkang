# 크보깡 — 어드민 기획서

> 위치: `kbokkang/apps/admin` (Next.js). 공통 코드는 `@kbokkang/shared` 사용.
> `00_통합기획서.md`의 공통 규칙을 전제로 한다. 데이터 스키마·포인트 값은 통합기획서 5·6장 참조.
> **개발 순서상 어드민을 앱보다 먼저 만든다.** 어드민 구현 과정에서 스키마가 확정된다.
> **어드민 안에서는 화면(UI)을 스키마보다 먼저 만든다** — 목업 데이터로 화면을 완성한 뒤,
> 거기서 드러난 요구를 반영해 스키마를 확정하고 연결한다(통합기획서 2장).

---

## 1. 목적

- 카드 150장 규모의 데이터를 코드 배포 없이 관리.
- 유저·뽑기·예측·정산 현황을 운영자가 확인/조치.
- 어드민 구현으로 백엔드/DB 구조를 먼저 안정화 → 앱 개발 기반 마련.
- 화면을 먼저 만들어 **필요한 데이터의 형태를 실물로 확인**한 뒤 스키마를 확정.

## 2. 기술

- React / Next.js (웹). 화려한 UX 불필요, 기능 우선.
- Supabase 연동(DB, Storage, Auth). 어드민 접근은 운영자 계정만(역할 기반 접근 제어).

---

## 3. 화면 구성

> 사이드바 메뉴(평면 8개, 구현 확정):
> `대시보드 · 카드 관리 · 카드 일괄 업로드 · 유저 관리 · 경기 관리 · 구단 관리 · 통계 · 규칙 확인`
> 로그인은 사이드바 밖(별도 라우트). 사이드바 하단에 로그아웃 + `admin` 배지.

### 3.1 로그인

- 운영자 전용 로그인. 일반 유저 접근 차단(role = admin 체크).

### 3.2 대시보드 (홈)

- 요약 지표: 총 유저 수, 오늘 활성 유저, 총 카드 수(등급별), 오늘 뽑기 횟수, 오늘 경기/정산 상태.

### 3.3 카드 관리 ★핵심

#### 카드 목록

- 테이블: 도감번호, 이미지 썸네일, 이름, 등급, 종류, draw_weight, 시즌여부, 생성일.
- 필터: 등급별, 종류별, 시즌여부. 검색: 이름/도감번호.
- 정렬: 도감번호순(N01→M03).

#### 카드 추가 (등록 폼)

입력 항목:

- 이름 (text)
- 등급 (select: 일반/레어/에픽/레전드/신화)
- 종류 (select: 선수/마스코트/아이템)
- 이미지 업로드 (→ Supabase Storage, image_url 저장)
- draw_weight (int, 기본 1)
- 시즌여부 (checkbox, 기본 false)

자동 처리:

- **도감번호 자동 부여**: 등급 선택 시 해당 등급 접두어 + 다음 번호(예: 에픽이 5장이면 E06).
  - 폼에는 입력란을 두지 않고 미리보기만 표시. **실제 부여는 서버에서 계산**(클라 입력 신뢰 금지).
- 판매가/환급가는 저장 안 함(등급 기준 상수로 앱/어드민에서 계산).
- **이미지 없이 먼저 등록 가능**(`image_url` nullable). 이미지는 나중에 채운다.

#### 카드 일괄 업로드 (별도 메뉴)

목표 150장을 1장씩 등록하는 부담을 줄이기 위한 경로. 위 등록 폼과 별개 화면.

- 이미지 여러 장 드래그앤드롭(한 번에 최대 50장, 5MB/장).
- 파일명에서 카드 이름 후보 자동 추출(확장자·앞쪽 번호 접두어 제거).
- 등급·종류를 일괄 기본값으로 지정 후 개별 수정. 도감번호는 목록 순서대로 순차 부여(미리보기 제공).
- 이름이 빈 항목이 있으면 등록 차단.

#### 카드 수정 / 삭제

- 수정: 이름, 등급, 종류, 이미지, draw_weight, 시즌여부.
  - **등급 변경 시 도감번호 재부여**(확정): 새 등급의 다음 번호를 부여하고, 폼에서 기존 번호가
    비게 된다는 경고를 표시한다. 비워진 번호는 재사용하지 않는다.
- 삭제: **soft delete**(확정). 이미 유저가 보유한 카드와의 정합성 때문. 하드 삭제는 보유자 없을 때만.
  - 삭제된 카드는 목록에서 제외되고 뽑기 대상에서도 빠진다. 복구 가능.
  - 도감번호는 삭제 후에도 재사용하지 않는다.

### 3.4 유저 관리

#### 유저 목록

- 테이블: 닉네임, 응원팀, 보유 포인트, 도감 진행률(보유 종수/전체), 가입일.
- 검색: 닉네임.

#### 유저 상세

- 기본 정보(닉네임, 응원팀, 포인트, 가입일).
- 보유 카드 목록(카드별 수량).
- 도감 진행률(등급별).
- **뽑기 이력**: 언제 어떤 뽑기(일반/프리미엄)로 무슨 카드 뽑았는지, 중복/환급 여부. (draws 테이블)
- 포인트 변동 내역(point_transactions).
- 운영 조치: 포인트 수동 지급/차감(사유 기록 → reason=admin_adjust).

### 3.5 경기 / 예측 관리

- **하루 단위 조회**(확정). KBO는 하루 최대 5경기라 목록이 짧다. 페이지네이션 없음.
  - 진입 시 **무조건 오늘**. 이전/다음 날 이동 + 캘린더로 날짜 선택.
- 경기 목록: 시작 시각, `원정 VS 홈`(엠블럼은 가운데를 향하도록 배치, 홈 팀에 `홈` 배지),
  스코어, status(scheduled/closed/live/aggregating/settled), 예측 분포.
- 크롤링 상태 확인: **선택한 날짜** 기준. 수집 0건 / 결과 미수집(종료됐는데 스코어 없음) 경고.
  - 상태 필터와 무관하게 그날 전체를 집계해야 한다(필터 걸린 상태로 판단하면 오판).
- **수동 정산**: 크롤링 실패/오류 시 운영자가 결과 입력 → 정산 트리거.
  - `closed`/`live`/`aggregating`만 가능. `scheduled`(시작 전)·`settled`(완료)는 차단.
  - 무승부 허용(KBO는 무승부가 있음).
- 예측 로그(경기 상세): 예측 분포(원정/홈 비율, 적중 수, 지급 포인트 합계) + 유저별 예측 내역.

### 3.6 통계

- 카드별 보유 현황(어떤 카드가 많이/적게 풀렸는지).
- 등급별 뽑기 실제 분포(설정 확률 vs 실제 — 확률 검증).
- 포인트 유입/소비 추이.

### 3.7 구단 관리

> 원래 이 문서에 없던 화면. `teams` 테이블은 스키마에 있는데 관리 화면이 누락돼 있었다.
> 앱 온보딩의 응원팀 선택이 이 데이터에 의존하므로 필요하다.

- 구단 목록: 팀명, 약칭, 팀 컬러, 로고.
- **로고 업로드**(→ Supabase Storage, `teams.logo_url`). 로고가 없으면 팀 컬러 원형으로 대체 표시.
- 팀명·약칭·컬러 수정.

### 3.8 규칙 확인 (읽기 전용)

- 뽑기 확률(일반/프리미엄), 포인트 수급·소비 값, 등급별 판매·환급가를 표로 확인.
- 이 값들은 `packages/shared` 하드코딩이라 어드민에서 수정하지 않는다.
  운영 중 "확률이 뭐였지" 확인용. 향후 DB로 옮기면 편집 가능해진다.

---

## 4. 어드민에서 카드 등록 워크플로우 (운영 흐름)

```
1. AI로 카드 이미지 생성 (등급별 프롬프트, 통이미지)
2. 어드민 > 카드 추가 진입
3. 이름·등급·종류·draw_weight 입력, 이미지 업로드
4. 저장 → 도감번호 자동 부여, Storage 업로드, cards 레코드 생성
5. 목록에서 확인
```

## 5. 권한/보안

- 어드민 라우트 전체를 role=admin 가드로 보호.
- Supabase RLS: cards 테이블 쓰기는 admin만, 읽기는 앱 유저 허용.
- 이미지 업로드 버킷 권한 설정.
